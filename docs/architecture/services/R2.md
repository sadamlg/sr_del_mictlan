# Medios públicos con Cloudflare R2

Esta guía empieza por el recorrido que implementa el proyecto: cómo una clave de imagen almacenada en PostgreSQL o declarada en un componente se convierte en una URL pública de R2. Después explica cómo configurar y comprobar el bucket. El inventario de archivos, la entrega CDN y los costos quedan como referencia posterior.

## 1. Cómo llega una imagen a la página

El proyecto guarda los archivos en R2 y conserva en PostgreSQL sólo claves relativas, por ejemplo `images/catalog/calios-product.png`. `MEDIA_BASE_URL` aporta el origen público del bucket; el código agrega la clave y forma la URL final.

```text
.env (raíz)                         clave del objeto
MEDIA_BASE_URL ──┬─ Compose ───────┬─ backend: crea las URL del catálogo
                 │                 └─ frontend: entrega el origen a la landing
                 └──────────────────────────────┬
                                                ↓
                    https://<bucket-publico>.r2.dev/images/...
```

La configuración y el código se conectan así:

1. [`compose.yaml`](../../../compose.yaml) lee `MEDIA_BASE_URL` del `.env` de la raíz y la pasa tanto al backend como al frontend.
2. [`backend/src/catalog/catalog-handler.js`](../../../backend/src/catalog/catalog-handler.js) combina el origen con `imageKey` y `lifestyleImageKey` para construir las URL que devuelve `GET /api/catalog/products`.
3. [`frontend/src/app/page.js`](../../../frontend/src/app/page.js) pasa el origen a los componentes de la landing. [`frontend/src/lib/media-url.js`](../../../frontend/src/lib/media-url.js) forma las URL para el hero y otros medios.
4. [`frontend/next.config.mjs`](../../../frontend/next.config.mjs) permite a `next/image` solicitar imágenes desde el origen configurado. En desarrollo, las URL HTTP de localhost o de la LAN evitan el optimizador; el origen HTTPS de R2 no usa esa excepción.
5. [`backend/src/catalog/media.js`](../../../backend/src/catalog/media.js) y el helper del frontend validan las URL y las claves relativas. La aplicación no necesita credenciales de escritura: la carga se hace manualmente desde el dashboard.

La misma base pública se usa en hero, encabezado, modal de edad, FAQ y fichas del catálogo. No se guardan URL completas de `r2.dev` en PostgreSQL; las claves siguen siendo estables si cambia el origen.

## 2. Obtener la URL pública del bucket

La URL que necesita la aplicación aparece en la configuración pública del bucket; no es el endpoint S3 ni la dirección de una imagen individual.

1. En el dashboard de Cloudflare, abre **Storage & databases → R2 Object Storage**.
2. Selecciona el bucket que contiene la carpeta `images/`, en este proyecto `sr-del-mictlan`.
3. Abre la pestaña **Settings** y busca **Public Development URL**.
4. Si **Public URL Access** indica **Allowed**, copia el valor que aparece como **Public Bucket URL**. Ése es el origen que se configura en la aplicación.
5. Si el acceso no está permitido, pulsa **Enable** en **Public Development URL**. En el diálogo de confirmación escribe `allow`, pulsa **Allow** y copia después el **Public Bucket URL**.

El valor tiene este formato: `https://pub-<identificador>.r2.dev`. Si el bucket aún no existe, créalo desde **R2 Object Storage → Create bucket** con la clase **Standard**; los buckets nacen privados. Sube las imágenes desde **Objects** conservando las carpetas de [Inventario de medios](#inventario-de-medios), y vuelve a **Settings → Public Development URL** para habilitar y copiar la URL. [Crear buckets](https://developers.cloudflare.com/r2/buckets/create-buckets/) · [Habilitar una URL pública](https://developers.cloudflare.com/r2/buckets/public-buckets/)

Habilitar esta URL hace que los objetos del bucket puedan ser solicitados públicamente. Úsala sólo con medios destinados a visitantes. La raíz del dominio no muestra necesariamente una lista: comprueba una clave concreta, por ejemplo `<URL-pública>/images/hero-background.png`.

### URL configurada en este entorno

El responsable creó el bucket `sr-del-mictlan`, cargó los medios y compartió esta URL, que ya está configurada localmente en el `.env` de la raíz:

```env
MEDIA_BASE_URL=https://pub-47df7d3a7dd94d268c1661b2c36e0ae5.r2.dev
```

`.env` está ignorado por Git y no se incluye en commits. `.env.example` permanece sin un origen específico de cuenta. Configura sólo el origen: no agregues `/images`, una ruta de objeto, query, fragmento ni barra final. La aplicación agrega `images/...` desde sus claves.

Las doce rutas del inventario se abrieron correctamente en navegador; por ejemplo, el hero mostró sus dimensiones originales de 1672 × 941 px y las tres imágenes principales del catálogo, 1122 × 1402 px. Después se recrearon frontend y backend desde Compose: `GET /api/catalog/products` respondió HTTP 200 con las seis URL de producto bajo el origen R2, la ruta de optimización de Next.js respondió `HTTP 200 image/png` para Calios y la landing local mostró las tres fichas del catálogo.

## 3. Configurar la integración local

Para cambiar la base del bucket en una instalación local:

1. Copia el origen público que aparece en R2 y ponlo en `MEDIA_BASE_URL` del `.env` en la raíz del proyecto. Debe ser HTTPS y no llevar barra final.
2. Conserva las carpetas de cada objeto al cargarlo. Por ejemplo, la clave `images/hero-background.png` debe abrirse como `<MEDIA_BASE_URL>/images/hero-background.png`.
3. Recrea frontend y backend para que ambos procesos lean el mismo valor:

   ```bash
   docker compose up --detach --force-recreate backend frontend
   ```

   Este Compose ejecuta el servidor de desarrollo; para este cambio no necesita reconstruir la imagen.

4. Comprueba una ruta de imagen directa y las URL que devuelve `http://localhost:4000/api/catalog/products`. Las dos deben usar el origen `https://pub-47df7d3a7dd94d268c1661b2c36e0ae5.r2.dev`.

Cuando `MEDIA_BASE_URL` está vacío, la landing usa los archivos locales de `frontend/public/images`; el backend entrega las URL locales del frontend para el catálogo. El script de LAN puede sustituir la base por la IP privada del equipo, sólo durante el desarrollo. Para volver a ese comportamiento, vacía `MEDIA_BASE_URL` en el `.env` y recrea los servicios. Revisa [`docs/architecture/docker/COMPOSE.md`](../docker/COMPOSE.md) para el recorrido LAN.

La URL pública de desarrollo permite que el navegador solicite los objetos de R2, pero no convierte ni redimensiona las imágenes. [Cloudflare: buckets públicos](https://developers.cloudflare.com/r2/buckets/public-buckets/)

### Límites por entorno

- `r2.dev` es para desarrollo y staging, tiene límites variables y no se debe usar como origen de producción.
- No se deben cargar documentos privados: todo objeto de este bucket está destinado a visitantes una vez habilitado el acceso público.
- Producción usará un bucket separado y un dominio propio; DNS, dominio y entrega pública de producción corresponden a la fase 10.
- No agregues claves de API, tokens, credenciales S3 ni permisos de escritura a Next.js, Express o el navegador.
- Stripe Checkout no está implementado en esta fase. La fase 06 definirá su `STRIPE_MEDIA_BASE_URL` cuando el flujo de pago necesite URLs HTTPS que Stripe pueda descargar.

Cloudflare limita la URL de desarrollo y recomienda un dominio personalizado para producción y para usar controles, caché y administración de tráfico. [Detalles de URL pública de desarrollo](https://developers.cloudflare.com/r2/buckets/public-buckets/) · [Límites de R2](https://developers.cloudflare.com/r2/platform/limits/)

## 4. Verificación de los objetos

Las claves deben conservar exactamente los nombres y carpetas de la sección [Inventario de medios](#inventario-de-medios). Verifica:

- cada objeto responde por HTTPS y corresponde a la imagen esperada;
- la API del catálogo devuelve las URL de frente y ambiente bajo `MEDIA_BASE_URL`;
- hero, marca, calavera, etiqueta de agave y ambos fondos se resuelven desde el bucket;
- las fichas locales siguen usando las claves `images/catalog/...`;
- el navegador no muestra errores de dominio permitido de `next/image` ni errores de carga de medios.

Ejemplo para revisar un objeto conocido desde una terminal con salida a Internet:

```bash
curl --fail --head \
  https://pub-47df7d3a7dd94d268c1661b2c36e0ae5.r2.dev/images/hero-background.png
```

El endpoint de R2 no es un servicio de carga del sitio. La carga del MVP se hace manualmente desde el dashboard, y PostgreSQL guarda las claves y metadatos, no los archivos.

### Recursos de la aplicación que no van al bucket

- `frontend/src/app/favicon.ico` pertenece a Next.js y se sirve desde la aplicación.
- Los SVG de ejemplo no utilizados (`file.svg`, `globe.svg`, `next.svg`, `vercel.svg` y `window.svg`) no forman parte de los medios. Si alguno se necesita, debe incorporarse primero como recurso utilizado por la aplicación.

### Optimización y CDN

El dashboard de R2 almacena los PNG originales; no produce tamaños derivados ni formatos convertidos. Las imágenes de `next/image` pasan por el optimizador de Next.js según las opciones `sizes` de cada componente y el host permitido en `next.config.mjs`. Hero y fondos de escaparate usan `<picture>`/`<img>`; el fondo de la colección selecciona el archivo móvil en pantallas pequeñas. El hero usa `getImageProps`, por lo que su URL y variantes entregadas deben comprobarse en el navegador por entorno.

R2 entrega los objetos, pero no los transforma. Las transformaciones de Cloudflare Images son un servicio separado y opcional; no está habilitado en esta implementación. En el plan Free se incluyen hasta 5,000 transformaciones únicas por mes; las nuevas transformaciones que excedan el límite responden con error. Revisa las [reglas y precios vigentes de Cloudflare Images](https://developers.cloudflare.com/images/pricing/) antes de habilitarlo.

Para usar la caché CDN de Cloudflare con objetos de R2, conecta un dominio personalizado al bucket y revisa sus reglas de caché. `r2.dev` no ofrece esa configuración de caché. La entrega con dominio y CDN de producción queda para la fase 10. Consulta [caché CDN para R2](https://developers.cloudflare.com/cache/interaction-cloudflare-products/r2/) y [dominios públicos de R2](https://developers.cloudflare.com/r2/buckets/public-buckets/).

### Cuotas, precios y alertas

En R2 Standard se incluyen por mes 10 GB-mes de almacenamiento, 1 millón de operaciones Clase A y 10 millones de Clase B. El egreso desde R2 no tiene costo. El uso que exceda los niveles incluidos se factura según la [tabla vigente de precios de R2](https://developers.cloudflare.com/r2/pricing/); Cloudflare redondea el consumo a la siguiente unidad facturable.

Cloudflare Images Free incluye 5,000 transformaciones únicas al mes. En el plan de pago, las transformaciones adicionales cuestan actualmente USD 0.50 por cada 1,000 únicas; el almacenamiento y la entrega de imágenes guardadas en Images tienen cobros separados. Consulta la [tabla oficial de precios de Images](https://developers.cloudflare.com/images/pricing/), ya que sus tarifas pueden cambiar.

Las alertas de presupuesto se configuran desde la cuenta de Cloudflare. Suman el uso facturable de productos en la cuenta, no sólo R2; notifican al alcanzar el umbral, pero no detienen el servicio. Revisa si ya existe una alerta y aprueba el umbral antes de crear otra. [Alertas de presupuesto](https://developers.cloudflare.com/billing/manage/budget-alerts/)
