# Medios públicos con Cloudflare R2

Esta guía describe el recorrido de los medios desde sus archivos de origen hasta las variantes responsivas que el navegador solicita directamente al dominio CDN de R2. También explica cómo configurar el bucket, generar y publicar las variantes, comprobar su entrega y considerar sus costos.

> Usa buckets y credenciales separados por entorno. Esta guía describe el procedimiento y los nombres de variables; los nombres de bucket, URL y resultados de despliegue se registran fuera del manual.

## 1. Cómo llega una imagen a la página

El proyecto guarda los archivos en R2 y conserva en PostgreSQL sólo claves relativas, por ejemplo `images/catalog/calios-product.png`. `MEDIA_BASE_URL` aporta el origen público del bucket; el código agrega la clave y forma la URL final.

```text
PostgreSQL: claves originales ──> backend: URL del objeto original ──┐
                                                                      ├─> navegador: <picture> + srcset WebP
Frontend: archivos declarados ──> srcset de variantes responsivas ──┘          │
                                                                                ↓
                                                               https://<dominio-cdn>/images/...
```

La configuración y el código se conectan así:

1. [`compose.yaml`](../../../compose.yaml) lee `MEDIA_BASE_URL` del `.env` de la raíz y la pasa tanto al backend como al frontend.
2. [`backend/src/catalog/catalog-handler.js`](../../../backend/src/catalog/catalog-handler.js) combina el origen con `imageKey` y `lifestyleImageKey` para construir las URL que devuelve `GET /api/catalog/products`.
3. [`frontend/src/app/page.js`](../../../frontend/src/app/page.js) pasa el origen a los componentes de la landing. [`frontend/src/lib/media-url.js`](../../../frontend/src/lib/media-url.js) forma las URL para el hero y otros medios.
4. [`frontend/src/components/media/responsive-media-image.js`](../../../frontend/src/components/media/responsive-media-image.js) y [`frontend/src/lib/media-url.js`](../../../frontend/src/lib/media-url.js) construyen un `srcset` de variantes WebP. El navegador pide la variante adecuada directamente al dominio de R2; Next.js no procesa ni entrega los bytes de estas imágenes.
5. [`backend/src/catalog/media.js`](../../../backend/src/catalog/media.js) y el helper del frontend validan las URL y las claves relativas. La aplicación no necesita credenciales de escritura: la carga se hace manualmente desde el dashboard.

La misma base pública se usa en hero, encabezado, modal de edad, FAQ, fichas del catálogo, carrito e historial de pedidos. No se guardan URL completas del proveedor en PostgreSQL; las claves originales siguen siendo estables si cambia el dominio CDN. El backend y Stripe pueden seguir usando los objetos originales; el navegador recibe las variantes responsivas.

## 2. Obtener la URL pública del bucket

`MEDIA_BASE_URL` es el dominio público que precede a las claves de objeto; no es el endpoint S3 ni la dirección de una imagen individual. En Staging y Production se conecta un dominio personalizado para usar la caché CDN. La URL `r2.dev` queda para desarrollo.

Para desarrollo local que usa la URL de prueba `r2.dev`:

1. En el dashboard de Cloudflare, abre **Storage & databases → R2 Object Storage**.
2. Selecciona el bucket de desarrollo y abre **Settings → Public Development URL**.
3. Si se necesita activar la URL, pulsa **Enable** en **Public Development URL**. En la confirmación escribe `allow` y pulsa **Allow**; el bucket quedará disponible en Internet bajo la URL de Cloudflare. Desactiva esta URL cuando ya no se necesite.
4. Copia el **Public Bucket URL** y úsalo como `MEDIA_BASE_URL` local.

Para Staging o Production, conecta el dominio CDN del entorno:

1. Selecciona el bucket correspondiente y abre **Settings → Public access → Custom Domains**.
2. Pulsa **Connect Domain**, escribe el hostname de medios de ese entorno y continúa.
3. Revisa el registro DNS que Cloudflare agregará y confirma **Connect Domain**.
4. Espera a que el estado del dominio y TLS aparezca como activo; configura su hostname como `MEDIA_BASE_URL`.

Conectar un dominio personalizado publica el bucket en ese hostname. Mantén en él sólo medios públicos aprobados. No es necesario habilitar `r2.dev` además del dominio personalizado. Cloudflare agrega el CNAME al conectar el dominio; no crees un CNAME hacia una dirección `r2.dev`. Si el bucket aún no existe, créalo desde **R2 Object Storage → Create bucket** con la clase **Standard**; los buckets nacen privados. Sube los originales y variantes desde **Objects**, conservando las carpetas de [Inventario de medios](#inventario-de-medios). [Crear buckets](https://developers.cloudflare.com/r2/buckets/create-buckets/) · [Buckets públicos y dominios personalizados](https://developers.cloudflare.com/r2/buckets/public-buckets/) · [Habilitar caché de R2](https://developers.cloudflare.com/cache/interaction-cloudflare-products/r2/)

La raíz del dominio no muestra necesariamente una lista: comprueba una clave concreta, por ejemplo `<MEDIA_BASE_URL>/images/hero-background.png`.

### Perfiles por entorno

| Perfil | Bucket y origen |
|---|---|---|
| Local | Bucket local; puede usar archivos públicos locales o una URL de desarrollo R2 |
| Staging | Bucket exclusivo y dominio personalizado/CDN de Staging |
| Production | Bucket y dominio de medios exclusivos de Production; no usar `r2.dev` |

Configura `MEDIA_BASE_URL` en Backend y Frontend, y `STRIPE_MEDIA_BASE_URL` en Backend, con el origen aprobado para el mismo entorno. El valor contiene sólo esquema y host, sin `/images`, ruta de objeto, query, fragmento ni barra final. Mantenlo fuera del repositorio si identifica una cuenta o bucket.

## 3. Configurar la integración local

Para cambiar la base del bucket en una instalación local:

1. Configura ImageMagick 7 con soporte WebP en el equipo de trabajo.
2. Genera las variantes locales desde los originales versionados en `frontend/public/images`:

   ```bash
   ./scripts/generate-r2-media-renditions.sh
   ```

   El script crea 40 variantes en `frontend/.generated/r2-media/images/`, sin añadirlas a `frontend/public` ni al contexto del build de Production. Los anchos corresponden a los `srcset` usados por la interfaz. El servidor local sigue usando los originales de `frontend/public/images` como fallback.

3. Configura el dominio público del bucket en `MEDIA_BASE_URL` del `.env` en la raíz del proyecto. Debe ser HTTPS y no llevar barra final. Para Staging y Production usa el dominio personalizado con CDN del bucket del entorno correspondiente; conserva `r2.dev` para desarrollo cuando no haya un dominio CDN disponible.

4. Carga los originales desde `frontend/public/images` y las variantes desde `frontend/.generated/r2-media/images`, conservando sus rutas relativas. El contenido de esa carpeta generada se publica bajo la clave `images/`; por ejemplo, `frontend/.generated/r2-media/images/hero-background-640.webp` se sirve como `<MEDIA_BASE_URL>/images/hero-background-640.webp`.

5. Recrea frontend y backend para que ambos procesos lean el mismo valor:

   ```bash
   docker compose up --detach --force-recreate backend frontend
   ```

   Este Compose ejecuta el servidor de desarrollo; para este cambio no necesita reconstruir la imagen.

6. Comprueba una variante WebP directa y las URL originales que devuelve `http://localhost:4000/api/catalog/products`. Ambas deben usar el valor configurado de `MEDIA_BASE_URL`; en el navegador, las imágenes responsivas deben solicitarse al dominio de medios, sin peticiones de imagen a `/_next/image`.

Cuando `MEDIA_BASE_URL` está vacío, la landing usa los archivos locales de `frontend/public/images`; el backend entrega las URL locales del frontend para el catálogo. El script de LAN puede sustituir la base por la IP privada del equipo, sólo durante el desarrollo. Para volver a ese comportamiento, vacía `MEDIA_BASE_URL` en el `.env` y recrea los servicios. Revisa [`docs/architecture/docker/COMPOSE.md`](../docker/COMPOSE.md) para el recorrido LAN.

La URL `r2.dev` de desarrollo permite solicitar objetos, pero no ofrece caché CDN, WAF ni administración de bots, y no convierte ni redimensiona las imágenes. Las variantes responsivas se generan localmente antes de publicarlas. [Cloudflare: buckets públicos](https://developers.cloudflare.com/r2/buckets/public-buckets/) · [Caché CDN para R2](https://developers.cloudflare.com/cache/interaction-cloudflare-products/r2/)

### Límites por entorno

- `r2.dev` es para desarrollo y tiene límites variables. Staging y Production usan dominios personalizados para entregar medios con CDN.
- No se deben cargar documentos privados: todo objeto de este bucket está destinado a visitantes una vez habilitado el acceso público.
- Production usa un bucket y un dominio de medios separados de Staging; su dominio, DNS y publicación se preparan en la fase 10.
- El bucket privado de respaldos PostgreSQL es un recurso distinto: no activar acceso público ni compartir permisos con el bucket de medios. Consulta [POSTGRES-BACKUPS.md](POSTGRES-BACKUPS.md).
- No agregues claves de API, tokens, credenciales S3 ni permisos de escritura a Next.js, Express o el navegador.
- Stripe Checkout usa `STRIPE_MEDIA_BASE_URL` como origen HTTPS de imágenes que Stripe descarga durante Checkout; debe coincidir con los medios públicos del mismo entorno.

Cloudflare limita la URL de desarrollo y recomienda un dominio personalizado para producción y para usar controles, caché y administración de tráfico. [Detalles de URL pública de desarrollo](https://developers.cloudflare.com/r2/buckets/public-buckets/) · [Límites de R2](https://developers.cloudflare.com/r2/platform/limits/)

## 4. Verificación de los objetos

Las claves deben conservar exactamente los nombres y carpetas de la sección [Inventario de medios](#inventario-de-medios). Verifica:

- cada original y variante WebP solicitada responde por HTTPS y corresponde a la imagen esperada;
- la API del catálogo devuelve las URL originales de frente y ambiente bajo `MEDIA_BASE_URL`;
- hero, marca, calavera, etiqueta de agave, carrito, pedidos y fondos se resuelven desde el dominio del bucket;
- las fichas locales conservan las claves originales `images/catalog/...`;
- el navegador selecciona tamaños apropiados mediante `srcset`, no pide imágenes de contenido a `/_next/image` y no muestra errores de carga;
- las respuestas directas del dominio CDN muestran los encabezados de caché esperados para el entorno.

Ejemplo para revisar un objeto conocido desde una terminal con salida a Internet:

```bash
curl --fail --head \
  "${MEDIA_BASE_URL}/images/hero-background-640.webp"
```

El endpoint de R2 no es un servicio de carga del sitio. La carga del MVP se hace manualmente desde el dashboard, y PostgreSQL guarda las claves y metadatos, no los archivos.

### Recursos de la aplicación que no van al bucket

- `frontend/src/app/favicon.ico` pertenece a Next.js y se sirve desde la aplicación.
- Los SVG de ejemplo no utilizados (`file.svg`, `globe.svg`, `next.svg`, `vercel.svg` y `window.svg`) no forman parte de los medios. Si alguno se necesita, debe incorporarse primero como recurso utilizado por la aplicación.

### Optimización y CDN

R2 almacena los originales y las variantes; no produce tamaños derivados ni convierte formatos. El script de ImageMagick genera WebP a los anchos adecuados para tarjetas, encabezados, fondos y componentes de cuenta. `ResponsiveMediaImage` y los fondos de la landing exponen esos archivos en `srcset`; el navegador elige el tamaño según `sizes` y la densidad de pantalla. La URL seleccionada apunta directamente a `MEDIA_BASE_URL`, así Railway no entrega la imagen al navegador ni ejecuta el optimizador para estos medios.

R2 entrega los objetos, pero no los transforma. Las variantes se generan antes de publicarlas; no se activa un servicio de transformación por solicitud. Cloudflare Images es un producto opcional separado y no forma parte de este flujo.

Conecta un dominio personalizado a cada bucket público de Staging y Production para entregar los objetos mediante la red CDN de Cloudflare. Revisa la caché y el `Cache-Control` efectivo en ese dominio; `r2.dev` es para desarrollo y no ofrece los mismos controles. Consulta [caché CDN para R2](https://developers.cloudflare.com/cache/interaction-cloudflare-products/r2/) y [dominios públicos de R2](https://developers.cloudflare.com/r2/buckets/public-buckets/).

Cloudflare almacena por defecto sólo ciertos tipos de archivo, entre ellos PNG y WebP. Un dominio personalizado vuelve elegibles esos objetos para la caché, pero no acredita que una respuesta específica haya sido un acierto: revisa `cf-cache-status` (`HIT`, `MISS` o `BYPASS`) y los encabezados `Cache-Control`. Si se reemplaza un archivo existente, purga su caché o espera a que venza su TTL antes de exigir que todos los puntos de presencia entreguen el contenido nuevo. [Tipos de archivo cacheados por defecto](https://developers.cloudflare.com/cache/concepts/default-cache-behavior/) · [Diagnosticar respuestas sin caché](https://developers.cloudflare.com/cache/troubleshooting/investigating-uncached-responses/)

### Cuotas, precios y alertas

Los costos de R2 dependen de almacenamiento medio, operaciones de lectura/escritura y reglas de ciclo de vida. La salida de datos desde R2 y las transformaciones de Cloudflare Images tienen modelos distintos; no los trates como una sola cuota. Revisa las [tarifas vigentes de R2](https://developers.cloudflare.com/r2/pricing/) y [Cloudflare Images](https://developers.cloudflare.com/images/pricing/) antes de elegir una arquitectura o estimar tráfico.

Las alertas de presupuesto se configuran desde la cuenta de Cloudflare. Suman el uso facturable de productos en la cuenta, no sólo R2; notifican al alcanzar el umbral, pero no detienen el servicio. Revisa si ya existe una alerta y aprueba el umbral antes de crear otra. [Alertas de presupuesto](https://developers.cloudflare.com/billing/manage/budget-alerts/)
